## Qwen GPU, latency and cancellation limits

The official model card reports theoretical minimum Transformers BF16 memory of **78.85 GB for 15 seconds of video**, rising to **88.52 GB for 30 seconds**, using FlashAttention 2. These figures include both Thinker and Talker. The lower-memory Thinking model cannot replace Instruct for spoken output. The table does **not** establish that one A100 80 GB can run our audio-only browser session with runtime/KV headroom. Short audio might fit; that is an inference requiring measurement. [Memory table](https://huggingface.co/Qwen/Qwen3-Omni-30B-A3B-Instruct#minimum-gpu-memory-requirements)

The reviewed vLLM-Omni pin places Thinker on GPU0 and Talker plus Code2Wav on GPU1. Its newer engine-duplex profile uses async chunking, while the same-revision generic realtime recipe still says to disable it; the [deferred qualification plan](QWEN_LIVE_QUALIFICATION.md) records this mode/documentation conflict. A one-card deployment would need separate colocation, memory and runtime proof; `30B-A3B` does not mean only3B parameters reside in GPU memory. No native WebSocket runtime was qualified.

The Qwen paper reports an optimized **234 ms theoretical cold first audio packet** at concurrency one and an audio real-time factor of 0.47. These are not an A100-browser SLA or end-to-end microphone latency. The paper's optimized pipeline and warm serving infrastructure differ from a new Modal worker. [Technical report, latency section](https://arxiv.org/html/2509.17765v1)

The current vLLM-Omni Qwen realtime tracker explicitly distinguishes a turn-based model from model-native simultaneous listening/generation. Automatic endpointing, continued input collection, cancellation, preservation of interrupting speech and heard-history reconciliation are separate serving gates. Its target UX is not evidence that every gate already works. Our PersonaPlex wire protocol cannot simply wrap Qwen's model step and retain its claims. [Maintainer tracker](https://github.com/vllm-project/vllm-omni/issues/7055)

## Background results and tools

Qwen's official audio function-call cookbook shows audio understanding producing textual tool-call markup; it sets `RETURN_AUDIO=False`. That example does not prove concurrent speech, asynchronous tool results or a Live function-result transport. Text conditioning is available, so a trusted background result can be part of a subsequent native audio response, but the exact serving history/tool adapter and actual spoken facts need qualification. [Official cookbook](https://github.com/QwenLM/Qwen3-Omni/blob/main/cookbooks/audio_function_call.ipynb)

Direct Alibaba realtime documents `conversation.item.create` carrying `{type: 'function_call_output', call_id, output}`, followed by response creation. Its tool-call response itself has no audio. The SDK exposes cancellation and subsequent native audio deltas; semantic VAD is supported on current 3.8/3.5 realtime models. This is an available protocol, not proof of nonblocking bank-result narration in our app. [SDK methods and tool schema](https://www.alibabacloud.com/help/en/model-studio/omni-realtime-python-sdk)

OpenRouter GPT Audio supports normal tools and text/audio messages, so a later trusted result can be provided to the next request. Aborting streaming stops processing/billing only for supported providers: OpenAI is listed as supported, Alibaba is listed as unsupported. This does not create a persistent audio session or cancel an independent banking job. [GPT Audio capabilities](https://openrouter.ai/openai/gpt-audio), [cancellation support](https://openrouter.ai/docs/api/reference/streaming)
