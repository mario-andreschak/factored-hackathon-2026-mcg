# Generic FLUJO platform evidence

FLUJO supplies reusable flow authoring, chat, MCP/tool dispatch, and execution interfaces. This guide makes a bounded part of that implementation inspectable from the Savia repository, including without a neighbor checkout or internet access. It separates generic platform source and offline checks from Savia's deployed customer path.

The immutable upstream pin is public main commit [`0be972ac7b748703d09e407ef96beba45ab17b2a`](https://github.com/mario-andreschak/FLUJO/commit/0be972ac7b748703d09e407ef96beba45ab17b2a), tree `5d7116fad792138eb0a6e6adf5a27ff19dc1c0f0`. A fresh `git ls-remote` observation on October 5, 2026 matched this commit to `refs/heads/main`; the timestamp and output are in the [source manifest](measurements/flujo-platform/source-manifest.json). That observation is dated, not a claim about a later branch tip. The public origin is [mario-andreschak/FLUJO](https://github.com/mario-andreschak/FLUJO).

The [offline package](measurements/flujo-platform/README.md) carries 39 exact upstream files, totaling 619,009 bytes, with Git blob IDs, SHA-256 hashes, immutable source links, and the original [MIT license](measurements/flujo-platform/source/LICENSE). Copies came from pinned Git objects rather than the neighbor checkout's modified working files. This is a review subset; it is not a complete buildable distribution.

These contracts allow an application to supply its own flow, prompts, model selection, and MCP services while keeping its domain schemas and policies outside generic FLUJO. The [release-note digest examples](measurements/flujo-platform/examples/release-note-digest.flow-spec.json) illustrate an independent use case: a configured repository-reading MCP tool feeds a summarization flow; [ordinary chat](measurements/flujo-platform/examples/chat-request.json) invokes it, [tool arguments](measurements/flujo-platform/examples/mcp-tool-request.json) fit the generic tool route, and [server-side run input](measurements/flujo-platform/examples/run-flow-input.json) chooses ephemeral execution with an explicit fail-on-approval policy. The names require real configured catalogs; these examples have not been run.

For integrations needing trusted execution restrictions, upstream also exposes an [execution adapter contract](measurements/flujo-platform/source/src/backend/execution/extensions/index.ts). It mints opaque contexts in trusted code and provides authorization, cancellation, commit, and tool-result hooks. The [default adapter](measurements/flujo-platform/source/src/backend/execution/extensions/configuredAdapter.ts) is `undefined`; [build configuration](https://github.com/mario-andreschak/FLUJO/blob/0be972ac7b748703d09e407ef96beba45ab17b2a/next.config.mjs#L90) selects an explicitly supplied trusted server module. A non-banking use could restrict a document-processing service to an owned workspace and validated tool results. This is a source-backed extension point, not a claim that an untrusted runtime plugin or a complete policy implementation was tested here.

## Durability and safety boundaries

The runner snapshots a resolved saved flow for a new conversation; [content-addressed snapshots](measurements/flujo-platform/source/src/backend/services/flow/executionSnapshot.ts) also clone and hash definitions. [Conversation execution locking](measurements/flujo-platform/source/src/backend/execution/flow/conversationExecutionLock.ts) serializes mutations for one workspace/conversation within a process and is reentrant. The [conversation log](measurements/flujo-platform/source/src/backend/execution/flow/conversationLog.ts) appends events, allocates sequence numbers, and reconstructs transcripts; the [state persistence layer](measurements/flujo-platform/source/src/backend/execution/flow/persistConversationState.ts) separates runtime-only fields from stored state. These mechanisms are inspectable, but this packet does not measure cross-process concurrency, crash/power-loss persistence, replay completeness, or long-running endurance.

[Recovery checkpoints](measurements/flujo-platform/source/src/backend/execution/flow/recoveryCheckpoint.ts) distinguish failure categories and track tool effects. Unknown side effects require manual action and disable automatic replay. Read-only/idempotent classifications depend on MCP annotations supplied by the tool definition; they are not proof that an external tool obeys those annotations. [Execution authority fencing](measurements/flujo-platform/source/src/backend/execution/flow/executionAuthority.ts) fails Persona-attributed durable mutations closed without lock-capable authority while preserving ordinary authority-free runs.

Approval is configurable and defaults to **false** for ordinary runs. The [approval decision code](measurements/flujo-platform/source/src/backend/execution/flow/resumeAfterApproval.ts) and [registry](measurements/flujo-platform/source/src/backend/execution/flow/toolApprovalRegistry.ts) support pending decisions and rejection; this does not provide customer consent or transaction authorization. [Local request guards](measurements/flujo-platform/source/src/utils/http/localRequest.ts) implement Host/Origin checks for local internal routes. They do not establish user identity. MCP roots are explicitly documented as advisory in the copied configuration types. None of these generic mechanisms substitutes for the Savia host's ownership checks or the banking MCP's policy.

## What was actually checked

On October 5, 2026, an isolated archive of the pinned source passed **104 tests across nine selected upstream suites**: FlowSpec compile/validate/save, direct chat routing, snapshot resolution, conversation serialization, mutation authority, recovery classification/effect marking, approval registry, approval decisions, and local request guards. The [receipt](measurements/flujo-platform/upstream-test-receipt.json), [per-test results](measurements/flujo-platform/upstream-tests.json), [output](measurements/flujo-platform/upstream-test-log.txt), and [replay script](measurements/flujo-platform/run-upstream-offline.cjs) expose the evidence.

Tests reused an existing dependency cache on Node `v22.13.1`, Windows x64. Eleven installed direct package versions differ from or are missing relative to the pinned lockfile, including Next `16.3.5` versus `16.3.8`; workspace links are resolved to their locked package versions in the receipt. No clean install, production build, full test suite, or transitive integrity audit was run. The selected suites use mocks, including provider/MCP/catalog/storage or command sinks. An in-process network API guard recorded zero attempts; it is not an operating-system sandbox.

Separately, the [repo-only smoke](measurements/flujo-platform/offline-smoke.mjs) loads the copied, unmodified retry module without dependencies. All [five checks](measurements/flujo-platform/offline-smoke-results.json) passed for time parsing, malformed values, bounded retries, rate-limit timing, and cancellation. `node verify-source.cjs` verifies every copied file against the recorded byte hashes and Git blob IDs. Run instructions are in the [package README](measurements/flujo-platform/README.md).

This evidence establishes inspectable generic source and narrow offline behavior at one revision. It does not establish Savia deployment identity, live providers or MCP interoperability, native agent isolation, bank authorization, customer-path acceptance, throughput, or held-out answer quality. Use [the product boundary](../FLUJO_PRODUCT_BOUNDARY.md), [deployment source map](../FLUJO_HACKATHON_DEPLOYMENT.md), and [Savia release candidate](RELEASE_CANDIDATE.md) for the separate domain source and runtime evidence. Nothing in this packet merges domain source into generic main or upgrades historical runtime measurements.
