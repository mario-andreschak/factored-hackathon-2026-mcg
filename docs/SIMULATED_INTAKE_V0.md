# Simulated unrecognized-charge intake v0

This is a private, single-customer prototype. Savia resolves a displayed transaction reference to an owned source transaction on the frontend server, opens the already owned FLUJO conversation, and asks the protected FLUJO action route to prepare a sandbox intake. The model cannot choose or call these five action tools. The customer confirms the exact prepared action in the UI; the backend then reads a persisted sandbox receipt before displaying its ID. Handoff IDs are also displayed only after a separate read.

The integration is disabled by default. Set `chat.action_enabled` to `true` in the private frontend config only after the matching FLUJO action route and delegated banking MCP source are installed. This setting never enables a live bank write. The MCP remains the existing private stdio server in the FLUJO worker; there is no remote MCP endpoint or extra container.

## Provisional policy

The R16 count is the number of distinct persisted, owner-readable sandbox unrecognized-charge cases whose server UTC `created_at` falls in `[now−24h, now)`, excluding the current transaction, plus the current distinct owned request. At three or more, the action prepares a verified human handoff. The count is private and is not sent to the browser. This is a sandbox measure, never a claim about all bank reports.

`sandbox_report_coverage_start` in the private MCP config declares the intended start of complete sandbox history, but the value alone grants no clearance. A trusted operator must seed/verify the synthetic ledger and run `python -m banking_mcp attest-sandbox-coverage --config PRIVATE_CONFIG --provenance synthetic:FIXTURE_ID`. This writes an attestation tied to the current SQLite ledger generation in the same transaction. A fresh, replaced, uninitialized or mismatched ledger yields `risk_data_complete=false`, a `null` count, and `missing_evidence` handoff. A deliberately attested complete empty ledger measures zero prior sandbox cases. The decision also hands off transactions older than 120 calendar days, future-dated transactions, and statuses other than `Approved`.

`synthetic_evidence_file` is a private, pinned JSON fixture with `build_id`, the snapshot's `source_fingerprint`, and per-transaction `historical_complaints` (`clear_in_snapshot`, `exact_open_case`, or `uncertain`), `duplicate_signal` (`clear`, `persistent`, or `unknown`), `fraud_score`, and `amount_usd`. It is operator supplied synthetic evidence, not a bank feed. Missing, changed, malformed or incomplete signals route to `missing_evidence`; a verified score of at least 70, USD amount of at least 1000, or R16 count of at least three routes to `high_risk`. An exact open historical signal or persistent duplicate routes to `duplicate_review` handoff in this narrower v0. Historical signals do not establish an exact charge-associated case. The issue #21 source separately verifies persisted local case receipts; it does not claim full historical R12/R15 policy acceptance.

Pending handles last ten minutes. Confirmation rechecks the original owner, current snapshot and transaction facts, coverage, and count. `(customer, transaction, action)` is unique in SQLite. A lost confirmation response is followed by a receipt read for the same pending handle, never another confirmation write. Savia persists the owner-bound action state before a confirmation attempt and exposes `GET /api/action/status` for refresh and manual status recovery; an absent receipt after an attempted write remains unverified and never becomes a prompt to confirm again. Only a read-back case earns `CMP-SBX-XXXXXXXX`; only a read-back handoff earns `HOF-XXXXXXXX`. A handoff packet records no human response. Spanish and Portuguese fallback text explicitly distinguishes an unverified action from a verified handoff and states that no refund or dispute resolution occurred.

Preparation requires a server-persisted lowercase UUIDv4 request ID. The MCP keys it to the admitted subject, customer, session and conversation, then derives the opaque pending handle from the private service token. It saves the original decision and public result atomically with the pending record. A retry with the same ID and target recovers the original intent after restart and rechecks local case evidence: a now-verified case is shown instead of another intake; an uncertain attempt stays unverified. A changed target/snapshot, expired pending, revoked session or changed derivation secret fails closed and never creates a fresh pending under the reused key. Rotate the private service token only after outstanding pending requests are resolved or expired.

An exact persisted case for the same owner and charge returns `decision: "existing_case"` only when its saved receipt and status are verified. FLUJO reads that receipt again before showing terminal `existing_case_verified`, without another confirmation call. Legacy, corrupt or uncertain records remain unverified. A retry of the original pending handle remains idempotent. A selected-charge human request rechecks the owned charge before saving its facts, provenance, reason and bounded `unanswered_questions`. Its stable request UUID and frozen payload deduplicate a lost-response retry; a changed target, snapshot, reason or questions cannot reuse that UUID. A saved packet can be recovered after snapshot rotation with its original provenance and a separate currentness disclosure. A no-charge human request carries its own UUID so unrelated requests in one conversation never share a handoff ID. Handoff insertion checks expiry and revocation while holding the SQLite writer. See [the issue #21 source contracts](ISSUE21_DATA_AND_RECEIPTS.md) for exact fields and uncertainty rules.

## Verification and limits

The source tests exercise owner denial, replay, concurrent confirmation, the 24-hour threshold, missing coverage, stdio action tools, frontend API mapping, Spanish and Portuguese fallback, and lost logout acknowledgment recovery. A private joined browser→FLUJO→MCP run against one matching synthetic snapshot is still required before this prototype is enabled in a worker. The currently running worker and organizer `CURRENT` pointer are intentionally unchanged. The separate 15-case audit pack is read-side evidence and does not establish action acceptance.

An exhausted prepare recovery stays unresolved and locked. Savia displays an opaque review reference derived only from its saved random action identity and tells the customer to share it with the team that provided demo access. This does not send a case or prove team pickup. The [private recovery triage runbook](RECOVERY_TRIAGE.md) describes how that team can count exhausted requests and inspect exact matching evidence in consolidated, read-only frontend and MCP ledger snapshots. The triage command cannot clear, retry, confirm, or change an action; an older case for the same charge does not prove consent for the lost preparation.
